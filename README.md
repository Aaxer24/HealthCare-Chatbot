# Medical Knowledge Chatbot

An interactive healthcare chatbot that uses retrieval-augmented generation over curated medical PDFs. The app retrieves relevant passages from a FAISS vector store, reranks the results, sends grounded context to Groq, and returns conversational answers with source citations and snippet previews.

## Features

- RAG over trusted medical PDFs stored in `data/`
- Streamlit chat interface with session history
- Groq chat model for low-latency responses
- BGE embeddings for stronger semantic retrieval
- Hybrid retrieval: BM25 keyword search fused with FAISS semantic search (reciprocal rank fusion),
  then cross-encoder reranking
- Query rewriting so informal/Hinglish input ("sugar ki problem") is searched as medical
  terminology ("diabetes mellitus symptoms"), plus multi-query fan-out for better recall
- Answer caching, so repeated questions cost zero Groq tokens
- Suggested follow-up questions under every answer
- Thumbs up/down feedback that feeds a review pipeline into the golden evaluation set
- Upload a report or prescription photo; OCR extracts the text and the bot answers about it
- Medical safety prompt with emergency-care guidance and uncertainty handling
- Source previews showing document names, pages, relevance scores, and snippets
- General-chat router so greetings and capability questions do not search PDFs
- Modular architecture: FastAPI backend + Streamlit UI, decoupled over HTTP
- Automated RAGAS evaluation pipeline (faithfulness, relevancy, context precision/recall)
- 31-question golden eval set, tracked as MLflow runs (params + RAGAS metrics per run)
- Data and vector-index versioning with DVC, backed by an S3 remote
- Optional LangSmith tracing of every retrieval/generation call
- 98-test pytest suite covering config, ingestion, normalization, retrieval, fusion, routing,
  caching, feedback, OCR, service, and API layers
- Dockerized as a single container, with CI/CD (GitHub Actions) building and deploying to AWS EC2 on every push,
  gated on a RAGAS eval regression check

## Setup

1. Create and activate a virtual environment.

```powershell
python -m venv venv
.\venv\Scripts\Activate.ps1
```

In this local project, your current environment is Conda-style, so these commands also work:

```powershell
.\venv\python.exe -m pip install -r requirements.txt
```

2. Configure secrets.

```powershell
Copy-Item .env.example .env
```

Add your Groq API key to `.env`.

3. Get the data and vector store. Either pull the versions already tracked in DVC (fast, no PDF
   parsing needed -- see [Data & Experiment Versioning](#data--experiment-versioning-dvc) for
   remote setup):

```powershell
.\venv\python.exe -m pip install "dvc[s3]"
dvc pull
```

   ...or rebuild them locally from the PDFs in `data/`:

```powershell
.\venv\python.exe create_memory_for_llm.py
```

Rebuild is required after changing PDFs or changing the embedding model. After rebuilding, run
`dvc add data vectorstore/db_faiss && dvc push` to version the new snapshot (see below).

4. Run the app.

```powershell
.\venv\python.exe -m streamlit run medibot.py
```

If you want the Streamlit UI to use the FastAPI backend locally, start the API first:

```powershell
.\venv\python.exe -m uvicorn src.api:app --host 127.0.0.1 --port 8000
```

Then in another terminal run:

```powershell
set API_BASE_URL=http://127.0.0.1:8000
.\venv\python.exe -m streamlit run medibot.py
```

## Containerization

The image runs **both** the FastAPI backend and the Streamlit UI inside a single container --
`docker/entrypoint.sh` starts the API on an internal-only port (`127.0.0.1:8000`), waits for it
to become healthy, then runs Streamlit in the foreground on the port the container publishes
(`$PORT`, defaulting to `8080`). There's no separate `api` container to wire up. On EC2 the
container binds `127.0.0.1:8080` (loopback only) and a separate Caddy container terminates HTTPS
in front of it -- see [Deployment](#deployment-aws-ec2).

The FastAPI backend's startup also pre-warms the embedding model, reranker, and FAISS index
(rather than lazily loading them on the first chat request) -- see `src/api.py`. This mainly
matters on scale-to-zero platforms (a cold start resolves during the container's own
startup/readiness window instead of a real user's first message eating a 15-30s delay), but is
harmless and still worth keeping on an always-on EC2 instance too -- it just means the container
takes a few seconds longer to report healthy after each restart, in exchange for consistent
first-request latency.

Build and run it locally:

```powershell
docker build -t healthcare-chatbot .
docker run --rm -p 8080:8080 --env-file .env healthcare-chatbot
```

Open `http://localhost:8080`.

The image:

- runs as a non-root user
- preloads embedding and reranker weights at build time (only Groq's API is needed at runtime, not Hugging Face Hub)
- performs startup validation for `GROQ_API_KEY` and the vector store files before serving traffic
- exposes a health check on `/_stcore/health`

### FastAPI backend

`src/api.py` exposes the same RAG/routing logic Streamlit uses, as a REST API on the internal
port:

- `POST /chat`
- `GET /health`

```json
{
  "prompt": "What is anemia?",
  "chat_history": [
    {"role": "user", "content": "Explain iron deficiency"},
    {"role": "assistant", "content": "Iron deficiency is ..."}
  ]
}
```

Streamlit talks to it over HTTP via `API_BASE_URL` (defaults to `http://127.0.0.1:8000`, correct
for the single-container setup) instead of calling the RAG service directly in-process --
see `src/api_client.py`.

## Deployment: AWS EC2

One-time setup, before the CI/CD pipeline can deploy:

1. Launch an EC2 instance -- Ubuntu Server LTS, `t3.small` or larger. 2GB+ RAM matters here:
   PyTorch, the embedding model, the cross-encoder reranker, and the FAISS index routinely use
   500MB-1GB+ together, which doesn't leave enough headroom on a 1GB `t3.micro` without adding
   swap space. Security group needs inbound `22` (SSH), `80` (HTTP) and `443` (HTTPS) allowed
   -- port 80 stays open because Let's Encrypt uses it to validate certificate renewals.
2. Install Docker on it:
   ```bash
   sudo apt-get update
   sudo apt-get install -y ca-certificates curl git
   sudo install -m 0755 -d /etc/apt/keyrings
   curl -fsSL https://download.docker.com/linux/ubuntu/gpg | sudo gpg --dearmor -o /etc/apt/keyrings/docker.gpg
   sudo chmod a+r /etc/apt/keyrings/docker.gpg
   echo \
     "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.gpg] https://download.docker.com/linux/ubuntu \
     $(. /etc/os-release && echo "$VERSION_CODENAME") stable" | \
     sudo tee /etc/apt/sources.list.d/docker.list > /dev/null
   sudo apt-get update
   sudo apt-get install -y docker-ce docker-ce-cli containerd.io
   sudo usermod -aG docker $USER
   ```
3. Add four repo secrets (Settings -> Secrets and variables -> Actions):

| Secret | Value |
| --- | --- |
| `EC2_HOST` | The instance's public IP |
| `EC2_USER` | `ubuntu` (or `ec2-user` for Amazon Linux) |
| `EC2_SSH_KEY` | The full contents of the instance's private key (`.pem`) |
| `GROQ_API_KEY` | Your Groq API key -- passed through to the running container |

Once those are set, push to `main` and CI/CD (below) builds and deploys automatically. To deploy
manually instead (from the instance itself, or over SSH):

```bash
docker pull ghcr.io/<owner>/<repo>:latest
docker stop healthcare-chatbot 2>/dev/null || true
docker rm healthcare-chatbot 2>/dev/null || true
docker run -d --name healthcare-chatbot --restart unless-stopped \
  -p 80:8080 -e GROQ_API_KEY=<your-key> ghcr.io/<owner>/<repo>:latest
```

The image doesn't go to a paid registry -- it's pushed to GitHub Container Registry (GHCR), which
authenticates with the workflow's own built-in token, no extra account or secret needed for that
part.

### HTTPS (Caddy + Let's Encrypt)

The app is served over HTTPS at **https://healthcare-chatbot.duckdns.org** by a
[Caddy](https://caddyserver.com) container that owns ports 80/443 on the host and reverse-proxies
to the app on loopback. Caddy obtains and renews the Let's Encrypt certificate automatically --
there is no certbot cron job to maintain.

The domain is a free [DuckDNS](https://www.duckdns.org) subdomain whose A record points at the
instance's public IP. **If the instance's public IP ever changes** (it does on stop/start, since
there's no Elastic IP attached), the DuckDNS record must be updated to match or the site breaks.

One-time setup on the instance:

```bash
sudo mkdir -p /etc/caddy
sudo tee /etc/caddy/Caddyfile > /dev/null << 'EOF'
healthcare-chatbot.duckdns.org {
	reverse_proxy 127.0.0.1:8080
}
EOF

docker run -d --name caddy --restart unless-stopped --network host   -v /etc/caddy/Caddyfile:/etc/caddy/Caddyfile:ro   -v caddy_data:/data   -v caddy_config:/config   caddy:2
```

`--network host` lets Caddy bind 80/443 directly and reach the app at `127.0.0.1:8080`; the
`caddy_data` volume persists issued certificates across container restarts (without it, every
restart re-requests a cert and can hit Let's Encrypt rate limits). Caddy handles the WebSocket
upgrade Streamlit needs automatically, and redirects plain HTTP to HTTPS with a 308.

Caddy is long-lived and is **not** managed by the CI/CD pipeline -- deploys only replace the app
container. That's also why the deploy publishes the app on `127.0.0.1:8080` rather than port 80.

## CI/CD

`.github/workflows/ci.yml` runs on every push/PR to `main`:

1. **`test`** -- installs dependencies, runs the full pytest suite. Gates everything below. (The
   suite mocks out the vector store, so it doesn't need `dvc pull`.)
2. **`build-and-deploy`** (push to `main` only, after tests pass):
   - Pulls `vectorstore/db_faiss` from the DVC S3 remote (the image bakes in whatever `dvc pull`
     retrieves, it doesn't regenerate the index at build time).
   - Runs a 6-question subset of the golden eval set through the live pipeline, scored on just
     `faithfulness`/`answer_relevancy`, and checks those against the floors in
     `eval/check_thresholds.py` -- fails the build if a change regressed retrieval or generation
     quality. Deliberately small and cheap: `GROQ_API_KEY` is shared with the deployed app, and
     Groq's free tier has a *daily* token cap (not just per-minute) -- `context_precision`/
     `context_recall` are skipped here because they call the judge once per retrieved chunk each,
     several times the cost of the other two. Run the full 31-question set with all four metrics
     locally for actual tuning (`evaluate_chatbot.py --metrics <comma-separated-list>` to pick a
     subset, `--limit N` to cap the question count).
   - Builds the Docker image, pushes it to GHCR, then SSHes into the EC2 instance to pull the new
     image and restart the container.

Six repo secrets are required (Settings -> Secrets and variables -> Actions): `EC2_HOST`,
`EC2_USER`, `EC2_SSH_KEY`, `GROQ_API_KEY` (see [Deployment](#deployment-aws-ec2)), plus
`AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` for the DVC pull (see below).

## Configuration

These values can be set in `.env` or Streamlit secrets.

| Variable | Purpose | Default |
| --- | --- | --- |
| `GROQ_API_KEY` | Groq API key | Required |
| `GROQ_MODEL` | Chat model | `openai/gpt-oss-120b` |
| `MODEL_TEMPERATURE` | Response randomness | `0.1` |
| `RETRIEVAL_K` | Initial retrieved chunks before reranking | `8` |
| `RERANK_K` | Final chunks after reranking | `5` |
| `ENABLE_RERANKING` | Enable cross-encoder reranking | `true` |
| `API_BASE_URL` | FastAPI base URL used by Streamlit | `http://127.0.0.1:8000` |
| `LOG_LEVEL` | Python logging level | `INFO` |
| `LANGCHAIN_TRACING_V2` | Enable LangSmith tracing (optional) | unset (disabled) |
| `LANGCHAIN_API_KEY` | LangSmith API key (optional, required if tracing is on) | unset |
| `LANGCHAIN_PROJECT` | LangSmith project name (optional) | `healthcare-chatbot` |
| `ENABLE_CACHE` | Cache answers to avoid repeat Groq calls | `true` |
| `CACHE_TTL_SECONDS` | How long a cached answer stays valid | `86400` |
| `CACHE_MAX_SIZE` | Max cached answers before LRU eviction | `512` |
| `ENABLE_HYBRID_SEARCH` | Fuse BM25 keyword hits with semantic hits | `true` |
| `ENABLE_QUERY_REWRITING` | Rewrite informal/Hinglish queries (1 extra LLM call) | `true` |
| `MULTI_QUERY_COUNT` | Extra query variations to retrieve with (0 disables) | `2` |
| `ENABLE_FOLLOW_UPS` | Suggest follow-up questions (1 extra LLM call) | `true` |
| `FEEDBACK_PATH` | Where thumbs up/down records are appended | `eval/feedback/feedback.jsonl` |

### Token budget

Each answered medical question costs several Groq calls: classification, answer-style, query
rewriting, multi-query generation, question condensing, the answer itself, and follow-up
suggestions. On Groq's free tier the daily token cap is **per organisation, not per key**, and it
is shared with CI — so if the quota starts biting, turn features off in this order:
`MULTI_QUERY_COUNT=0`, then `ENABLE_FOLLOW_UPS=false`, then `ENABLE_QUERY_REWRITING=false`.
Leave `ENABLE_CACHE=true`: it is the only setting that *reduces* usage.

## Data & Experiment Versioning (DVC)

`data/` (source PDFs) and `vectorstore/db_faiss/` (the generated FAISS index) are tracked with
[DVC](https://dvc.org) instead of committed to git directly -- git only holds the small `.dvc`
pointer files (`data.dvc`, `vectorstore/db_faiss.dvc`); the actual bytes live in an S3 remote.
This keeps git history free of ~50MB+ binary blobs while still giving every index snapshot a
reproducible, content-addressed version.

One-time setup, before `dvc pull`/`dvc push` work:

1. Create an S3 bucket for the remote and note its name/region.
2. `dvc remote add -d s3remote s3://<your-bucket>/dvcstore` then
   `dvc remote modify s3remote region <your-region>` (this is already configured in `.dvc/config`
   for this repo).
3. Configure AWS credentials locally (`aws configure`, or `AWS_ACCESS_KEY_ID` /
   `AWS_SECRET_ACCESS_KEY` env vars) with read/write access to that bucket. For CI, add those same
   two as repo secrets. A dedicated IAM user scoped to just that bucket
   (`s3:ListBucket` on the bucket ARN, `s3:GetObject`/`PutObject`/`DeleteObject` on `<bucket>/*`)
   is the more locked-down option, but this project just reuses the account's existing credentials.

Day to day:

```powershell
# Get the current tracked data + vector store (e.g. after cloning)
dvc pull

# After rebuilding the vector store or adding new source PDFs
dvc add data vectorstore/db_faiss
git add data.dvc vectorstore/db_faiss.dvc
git commit -m "Update vector store snapshot"
dvc push
```

## Evaluation

`evaluate_chatbot.py` runs the golden question set in `eval/golden_qa.json` (31 questions) through
the *actual* production RAG pipeline (same retrieval, reranking, and prompts as the live app)
and scores the results with [RAGAS](https://github.com/explodinggradients/ragas), using
Groq as the judge LLM and the same BGE embeddings as retrieval.

Metrics:

| Metric | What it measures |
| --- | --- |
| `faithfulness` | Whether every claim in the answer is supported by the retrieved context (hallucination check) |
| `answer_relevancy` | Whether the answer actually addresses the question asked |
| `context_precision` | Whether the retrieved chunks are relevant, ranked with the most useful ones first |
| `context_recall` | Whether the retrieved chunks contain everything needed to support the reference answer |

Setup and run:

```powershell
.\venv\python.exe -m pip install -r requirements.txt -r requirements-eval.txt
.\venv\python.exe evaluate_chatbot.py
```

Results are written to `eval/results/results.csv` (per-question scores) and
`eval/results/summary.json` (mean scores), a row is appended to `eval/results/history.csv`, a
summary table prints to the console, and the run is logged to MLflow (see below).

To evaluate a different question set, pass `--dataset path/to/file.json` with the same
`question` / `ground_truth` schema as `eval/golden_qa.json`. Pass `--limit N` to only run the
first N questions, and/or `--metrics faithfulness,answer_relevancy` to run a subset of the four
metrics -- both exist for cheap iteration against Groq's free-tier *daily* token cap (this is
what the CI eval-gate does, since `context_precision`/`context_recall` call the judge once per
retrieved chunk and are the most expensive). Re-run after any change to chunking, retrieval
parameters, prompts, or the embedding/reranker model to catch regressions before they reach
users.

### Growing the golden set from real feedback

Every answer carries thumbs up/down buttons. Ratings are appended to
`eval/feedback/feedback.jsonl` (a mounted volume on the server, so they survive redeploys).
Negative ratings mark the questions the pipeline handled badly, which makes them the most
valuable additions to the golden set:

```powershell
.\venv\python.exe scripts\review_feedback.py --list      # what users disliked
.\venv\python.exe scripts\review_feedback.py --stage     # write candidates file
# open eval/feedback/golden_candidates.json and write each ground_truth from the source PDFs
.\venv\python.exe scripts\review_feedback.py --promote   # merge into golden_qa.json
```

Ground truths are **never** generated automatically. Deriving one from the model's own (rejected)
answer would bake the failure into the metric, and not every complaint is a retrieval fault — some
are questions the corpus genuinely cannot answer, and adding those would permanently depress
scores for something the system was never given. The staging step is the human checkpoint.

Note that the CI eval-gate runs a fixed `--limit 6`, so the golden set can grow without slowing
down every push; the full set is for local runs.

### Experiment tracking (MLflow)

Every `evaluate_chatbot.py` run is logged as an MLflow run in the `healthcare-chatbot-rag-eval`
experiment: config params (model, `retrieval_k`, `rerank_k`, `enable_reranking`, chunk
size/overlap, embedding model, dataset) and the four RAGAS mean scores as metrics, with
`results.csv`/`summary.json` attached as artifacts. This makes it possible to directly compare
runs across different chunking or retrieval settings instead of eyeballing `history.csv`.

Runs are stored locally under `mlruns/` (gitignored). To browse them:

```powershell
.\venv\python.exe -m mlflow ui
```

then open `http://127.0.0.1:5000`.

### Tracing (LangSmith)

Set `LANGCHAIN_TRACING_V2=true` and `LANGCHAIN_API_KEY` in `.env` (see `.env.example`) to get a
trace in [LangSmith](https://smith.langchain.com) for every chat request and every
`evaluate_chatbot.py` call -- prompt, retrieved chunks, condensed question, latency, and token
usage per step. No code changes are needed beyond those two env vars; LangChain picks them up
automatically. Leave `LANGCHAIN_TRACING_V2` unset to disable tracing entirely (the default).

## Medical Safety

This chatbot is for educational information only. It does not diagnose conditions, prescribe treatment, or replace a licensed clinician. The prompt instructs the model to recommend urgent local care for emergency warning signs and to say when the documents do not support an answer.
